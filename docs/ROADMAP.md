# 路线图

LeagueAkari Plus 的路线图会优先围绕一个核心目标展开：

> 不是帮玩家作弊，而是帮玩家理解这一局应该怎么赢。

因此，前期重点不是堆功能，而是先把客户端连接、选人阶段识别、阵容分析和中文解释体验做好。

## 阶段 0：项目启动

这个阶段的目标是把项目方向定清楚，避免后面边做边改造成混乱。

- 创建项目仓库
- 明确产品定位：英雄联盟客户端增强与决策辅助工具
- 明确安全边界：不做影响游戏平衡的功能
- 明确第一版 MVP 范围
- 明确第一版技术路线：Rust / Tauri / Web 前端
- 检查原版 LeagueAkari 的开源协议，决定后续是 fork、重构，还是只借鉴思路

完成标准：

- 仓库结构清晰
- README 能说明项目是什么
- MVP 文档能说明第一版做什么、不做什么
- Rust / Tauri 技术规划能说明先验证什么、再开发什么
- 安全边界写清楚，后续功能都按这个边界判断

## 阶段 0.5：LCU 技术探针

这个阶段的目标是先验证最核心的不确定性：我们是否能稳定、安全地读取客户端公开给本地应用的 LCU 数据。

- 创建 Rust workspace
- 实现 `leagueakari-probe` 命令行工具
- 自动寻找并解析客户端 `lockfile`
- 读取当前召唤师资料
- 读取当前游戏阶段
- 监听选人阶段 session
- 输出双方已公开英雄、ban 位和当前 action
- 记录国服、国际服、WeGame 环境差异

完成标准：

- 客户端未启动时能给出清晰提示
- 客户端启动后能识别当前账号
- 进入选人阶段后能实时输出选人变化
- 断线或字段缺失时能给出明确状态，而不是崩溃

## 阶段 1：第一版 MVP

这个阶段的目标是做出一个真正可用的小版本。用户打开软件后，能连接客户端、看到账号信息，并在选人阶段得到有价值的阵容分析。

- 客户端连接状态检测
- 当前召唤师资料展示
- 最近 20 场战绩展示
- 选人阶段检测
- 符文推荐，并且必须由用户确认后才应用
- 基于规则的双方阵容分析
- 胜率区间展示，而不是假装精确到小数点
- 阵容短板提示，例如缺 AP、缺前排、缺开团、缺控制、后期不足
- 国服和国际服客户端兼容说明

完成标准：

- 用户能正常看到客户端连接状态
- 用户能在选人阶段看到双方阵容分析
- 分析结果能解释“为什么”，而不是只给一个数字
- 所有会修改客户端配置的操作都需要用户确认

## 阶段 2：数据质量

这个阶段的目标是让阵容分析更可信。第一版可以用规则模型，但规则需要有稳定的数据基础。

- 建立英雄标签库
- 建立英雄位置数据
- 建立版本数据更新流程
- 接入英雄胜率、登场率、Ban 率等公开数据
- 增加对线克制关系和英雄组合数据
- 增加本地缓存，避免每次启动都重新请求数据
- 在分析结果里显示可信度

完成标准：

- 每个英雄都有基础标签
- 阵容分析能感知版本变化
- 当数据缺失或位置不确定时，会降低可信度，而不是强行给结论

## 阶段 3：个人化推荐

这个阶段的目标是让推荐真正适合当前用户。很多工具只会推荐版本强势英雄，但玩家真正需要的是“我会玩的英雄里，哪一个最适合这一局”。

- 个人英雄池管理
- 常用位置记录
- 英雄熟练度或舒适度评分
- 基于个人英雄池的选人建议
- 基于当前阵容短板的补位建议
- 根据用户最近状态调整推荐权重

完成标准：

- 推荐结果不只看版本强度，也会考虑用户是否会玩
- 选人建议能给出清楚理由
- 用户可以手动维护自己的英雄池和位置偏好

## 阶段 4：扩展能力

这个阶段的目标是让项目更容易二开和长期维护。不是所有功能都要塞进主程序，适合拆成插件或数据源适配器。

- 插件 API
- 主题系统
- 数据源适配器
- 本地英雄标签包
- 社区维护的阵容分析规则包
- 可选的通知、战绩、符文、主题插件

完成标准：

- 新功能可以通过插件扩展
- 主题和数据源可以独立更新
- 主程序保持稳定，不因为每个新想法都变得臃肿

## 阶段 5：发布与维护

这个阶段的目标是让普通用户能稳定安装、更新和使用，而不是只停留在开发者电脑上。

- 应用打包
- 安装器
- 自动更新
- 发布说明
- 用户文档
- 常见问题说明
- 崩溃日志和问题反馈流程
- 应用签名策略

完成标准：

- 普通用户可以下载安装
- 新版本可以稳定更新
- 出问题时用户知道如何反馈
- 项目有清晰的版本记录和维护节奏
